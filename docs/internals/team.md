# Team service

Operating notes are in [Team service](../operations/team-service.md). This page keeps the decisions and traps.

- **Separate from the T3 server.** Accounts and organisations span environments and must exist for users who run no server at all, and the T3 server owns one machine's state. The service has its own database and release, and `npx t3` never depends on it. It is optional: nothing in T3 Code requires an account.
- **GitHub is the only identity.** There are no passwords, mail, or verification flows. GitHub has already verified the emails it reports, so the service trusts exactly those (`user_emails`, replaced on every sign-in) and nothing a user types.
- **Start, callback, poll.** Clients are bearer-token apps (web, desktop, mobile) and cannot receive the OAuth redirect themselves, so the browser lands on the service's callback page while the client polls. `start` stores an attempt row holding a random `state` (the only secret the poller needs), the PKCE verifier, and a 10-minute expiry, and returns the GitHub URL (PKCE S256). The callback atomically claims the attempt (`callback_at`), exchanges the code, upserts the user by GitHub numeric id, and parks the new session token on the row. `poll` deletes the row as it returns `complete` or `failed`, so the token is handed out once and never lives past ten minutes; expired rows are deleted on the next start or poll. Desktop and web share this path. The token sits in the row in plain text for that short window; only its sha256 is kept in `sessions`.
- **Bearer tokens and `Access-Control-Allow-Origin: *`.** Clients hold a token and send it in a header, never a cookie, so a cross-origin page cannot ride the user's session and wildcard CORS is safe. The callback is the only browser page and carries a locked-down CSP and `no-referrer`, since its URL holds a one-time code. Neither the code nor any token is logged.
- **Work email via GitHub.** Invitations and auto-join match any verified GitHub email, case-insensitively. A user adds their work email on GitHub to match; the next sign-in picks it up. `users.email` is only the primary verified email for display.
- **Domain claiming.** An owner can enable auto-join only for a domain of one of their own verified emails, never for public providers, and each domain belongs to one organisation (a unique index backs the check). Enabling it adds existing users with a verified email on that domain; signing in adds the user to matching organisations as `member`.
- **Last owner.** Owner rows are locked (`FOR UPDATE`) in the same transaction as the check, so two concurrent demotions cannot leave an organisation with no owner. Account deletion follows the same rule: a sole owner of an organisation with other members is refused.
- **Rate limit is per process.** Only the start endpoint is limited, in memory, keyed on the last `X-Forwarded-For` entry, so it assumes one instance behind one trusted proxy. The contract has no rate-limited code; the limit answers `unavailable`.
- **Dev data was wiped once.** Migration 2 drops the password-era tables instead of converting them.
- **Direct messages are keyed on the pair.** A conversation row has `user_a < user_b` (ordered with `LEAST`/`GREATEST` in SQL so the order matches the database collation) and a unique pair, so get-or-create is one `INSERT ... ON CONFLICT DO NOTHING` and is race-safe. There are no channels and no organisation requirement. Deleting an account deletes its conversations and messages for both people.
- **Message ids are the cursor.** `messages.id` is a `bigserial`, sent as a string. It grows with send order across the service, so it is the paging cursor (`id < before`) and the unread marker (`conversation_reads.last_read_message_id`, which only moves forward) without any timestamp tie-breaking. Unread is the peer's messages above the marker.
- **Events are SSE over `fetch`, not `EventSource`.** Clients authenticate with a bearer header and `EventSource` cannot send one, so `GET /v1/events` is read as a fetch stream. Delivery goes through the small `EventBus` interface, implemented in process; Postgres LISTEN/NOTIFY can replace it to run several instances. A ping every 25 seconds keeps proxies open and re-checks the session, so a revoked session ends the stream on the next ping rather than immediately. The sender also receives their own `message` event, for their other devices, with an unread count of 0.
- **Allowlist.** `TEAM_ALLOWED_EMAIL_DOMAINS` is checked against GitHub-verified emails at sign-in and again on every authenticated request against the stored `user_emails`. A refused sign-in also deletes that user's sessions. Checking per request is what makes enabling the list, or losing the email, take effect at once instead of after the 30-day session.
